# Test suite — what it guarantees

These [Pester](https://pester.dev) tests are the automated safety net for the
installer. They validate the **embedded agent manifest** (the `$agentManifestJson`
block inside `Setup-FabricAgenticWorkspace.ps1`) and its governance invariants, so
a change that would corrupt the agent organisation is caught before release.

They run automatically in GitHub Actions on every push/PR that touches the
installer, schema, or tests (see `.github/workflows/validate.yml`), and you can run
them locally at any time.

## How to run

**Easiest:** double-click `Run-Tests.bat` in this folder. It runs the whole suite
and shows a green/red summary. The path is resolved from the batch file's own
location (`%~dp0`), so it works for any user on any machine — no hard-coded paths.

**Manually** (from any terminal):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "Import-Module Pester; Invoke-Pester -Path '<path-to>\tests' -Output Detailed"
```

Expect **all tests passed / 1 skipped** on Windows PowerShell 5.1. The one skip is the
JSON-Schema test, which needs PowerShell 7 (`Test-Json -Schema`); GitHub Actions
runs on PowerShell 7, so it runs there and the full suite is exercised in CI.

## What each file checks

| File | What it guards | Why it matters |
|------|----------------|----------------|
| `Manifest.Helpers.ps1` | *(not a test)* Shared helpers that locate the installer, extract the embedded manifest JSON, and expose the allowed tool set. | Every test loads this; you never run it directly. |
| `Manifest.Tests.ps1` | The manifest is valid JSON, declares a `schemaVersion` + semantic `productVersion`, defines exactly **47 agents** with the expected tier counts (3 executive / 7 team-lead / 37 worker), and has unique ids, display names, filenames and numeric prefixes. Also validates the manifest against the JSON Schema (PS7/CI only). | Stops accidental duplication, miscounting, or a malformed manifest from shipping. |
| `Hierarchy.Tests.ps1` | Exactly one root (the Master), every `parent` resolves, the parent chain has no cycles, every `allowedChildren` entry resolves, only agents holding the `agent` tool may delegate, workers never delegate, and visibility / user-invocable flags match each tier. | Guarantees the delegation tree is coherent and can't form loops or dangling references. |
| `Tools.Tests.ps1` | Every `tools` entry uses only known capability tokens, no duplicates, and the delegation (`agent`) tool is never granted to a worker or to the default set. | Keeps the capability model well-formed. |
| `Tools.LeastPrivilege.Tests.ps1` | Every agent declares an **explicit** `tools` array (nothing relies on the default), the manifest default is **read-only** (`read`, `search`), only executives / team-leads may delegate, and read-only diagnostic roles are never granted `edit`. | Enforces least-privilege: broad capabilities are opt-in per role, not inherited. |
| `Version.Tests.ps1` | The installer's `$productVersion`, the embedded manifest `productVersion`, the README status heading, and the top CHANGELOG entry all agree. | Prevents version drift across the ~5 places a version is written. |
| `Generated.Tests.ps1` | Runs the installer in dry-run (`-EmitAgentsTo`) into a temp folder and checks the **actual generated files**: 47 agents exist, filenames match the manifest, frontmatter and `tools` match, the Master lists only its children (no direct-to-worker fallback) and carries the maintenance handoff; every agent has `Knowledge and skills` / `Playbook` / `Validation` sections and the WORK RESULT contract as mandatory final message; workers carry the approval-token rule and no delegation; every `execute` agent carries the terminal-hygiene rule; every delegating agent handles `agent not found` retries and empty returns; semantic-model agents reuse the Master-opened MCP connection (no `ListConnections` probe); **every tool an agent's body tells it to use (`ConnectFabric`, `powerbi-modeling-mcp`, `Fabric MCP/*`, terminal hygiene, delegation) is granted in that agent's frontmatter**, the MCP-connection bullet appears only on agents holding the modeling MCP, delegating agents carry the retry-after-write and bounded-parallel-dispatch rules, maintenance agents carry one vendor-refresh policy with stop conditions (no blanket *never reset*), terminal hygiene is tier-aware (script-writing only for agents with `edit`), and the Architect's PLAN / QA's VERDICT travel in the WORK RESULT `payload` field; leads have a roster and dispatch rules; Architect/QA have PLAN/VERDICT; no `fabric-tool-policy` or unresolved `.github` references; headings are well-formed. Also checks the emitted `starting-flow.md` (lean, Master connects via `ConnectFabric`), `working-flow-reference.md` (team protocol), `Get-SessionStatus.ps1` (present, parses, MCP line separate from tools, writes `session-status.last.txt`) and `.vscode/settings.json` (nested dispatch on, skill locations registered, no phantom extension paths). | Validates the real product the generator emits — structure **and** the specialist content — not just the manifest contract. |
| `VendorClone.Tests.ps1` | Loads `Update-VendorClone` from the installer and runs it against a throwaway local bare repository: a stale clone must reach `origin/HEAD` under `$ErrorActionPreference = 'Stop'`, local edits must be stashed (not lost), the call must be idempotent and must not change the caller's error preference. Failure paths: a blocked stash must leave the clone untouched (no reset), an unresolvable upstream must be reported as *could not reset* (never *already at upstream*), and a clone lacking only `origin/HEAD` must still refresh through the `@{upstream}` fallback. Identity guard: a vendor-named folder that is not its own repository root must be refused (the outer repository is neither stashed nor reset), a repository with the wrong `origin` must be refused, and `.git`/slash/case differences in the expected remote must be tolerated. | Regression guard for the refresh hardening in v0.7.0 (git's stderr progress under strict mode) and v0.7.1 (unchecked stash/reset exit codes; refresh could act on the containing workspace repository). |
| `Step1Prompts.Tests.ps1` | Launches the real installer with scripted answers and stops it right after Step 1: `y` at *Enter 1 or 2* behaves as option 1; a full path typed at the *name* prompt (either option) is used as-is and never crashes `Join-Path`; an invalid folder name is sanitised; an unrecognised choice re-asks instead of defaulting; a relative path for option 1 is rejected and re-asked. | Reproduces the first field-reported crash (`The given path's format is not supported`) so it cannot come back. |
| `UpdateSafety.Tests.ps1` | AST-loads `ConvertFrom-JsonLenient`, `Merge-JsonSettings` and `Merge-CodeWorkspace` from the installer: JSONC (comments, trailing commas) parses and user keys survive the settings merge without a `.bak`; an existing session workspace keeps user roots/settings while the managed root is renamed (no `$Path` shadowing) and a stale `.` root is dropped; a user-saved `.code-workspace` that opens the root via a relative path is detected from a fake `workspaceStorage`, only the dispatch setting and skill locations it lacks are reported (a relative entry equals its absolute form), the patch keeps user entries, writes no `.bak`/BOM and a second scan finds nothing; v0.7.2 `Update-UserSettingsInPlace` on JSONC fixtures: appends the dispatch flag and a workspace-relative skill block preserving comments, order and CRLF; flips an explicit `false`, merges only missing locations into an existing block keeping user entries (LF preserved); second run is a no-op and absolute/`~` paths are never written; creates the file when absent, keeps a BOM, refuses and leaves a broken file untouched; plus static checks that only declared agents are hashed into the manifest, the purge rejects `..`/absolute entries and verifies deletion, update commits stage retired files, the session workspace is never deleted before merging, vendor refresh is called with the expected remotes, winget payloads need exit 0 and backup cleanup sits outside the rollback block. | The user's workspace file, settings and own agents must survive every re-run; these are the invariants a re-run promises. |
| `SessionStatus.Tests.ps1` | Emits a scratch workspace, plants fake upstream skill folders (one registered, one new), a minimal `tool-status.json` (all CLI commands unresolvable, so no identity probe leaves the machine) and extra settings keys, then runs the emitted `Get-SessionStatus.ps1` from an unrelated working directory: the `ROOT` line must point at the scratch root, all sections print, MCP is reported as *installed* / *connected: none* and never as an available CLI, the new skill container is self-registered while existing keys survive, tools whose commands are missing flip to `found: false` with `_meta.lastSessionCheck` stamped, detect-only tools are not nagged about, identity reports *not logged in* without probing, and `session-status.last.txt` is written. A second run against a fake VS Code workspace-storage tree (`FABRIC_AGENTIC_WORKSPACE_STORAGE`) must name a user-saved `.code-workspace` that opens the root via a relative path without the nested-dispatch setting, and ignore one that opens a different folder. Every run pins the user settings path (`FABRIC_AGENTIC_USER_SETTINGS`) so the developer's real `%APPDATA%` cannot change the outcome; a third run with a JSONC user file carrying the flag and relative skill entries must report `enabled at user level`, count only relative entries that resolve under the root, and replace the saved-file warning with *need no patch*. | The status block is the Master's only startup input; this proves the script behaves on a machine that is not the maintainer's, offline. |

## What these tests do **not** cover

They validate the manifest **contract**, the generated files (structure and content
sections), the emitted settings and the vendor-refresh function. They do not run the
installer end-to-end against a real Fabric / VS Code
environment (no network, no tool installs), and they do not judge the
*behavioural* quality of an agent's prompt — only its structure, required sections and safety rules.
Behavioural quality is validated by real-world use and the installer's
post-generation self-test (`guardrail-status.json`).
