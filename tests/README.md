# Test suite — what it guarantees

These [Pester](https://pester.dev) tests check the installer
(`Setup-FabricAgenticWorkspace.ps1`): the embedded agent manifest (`$agentManifestJson`),
the files the installer generates, the helpers it ships and the documents of this
repository. The table below says what each test file proves.

GitHub Actions runs them on every push/PR that touches the installer, schema, tests,
the documents the workflow lists or the maintainer tooling in `.github/hooks`,
`.github/agents` and `.github/skills` (see `.github/workflows/validate.yml`). You can run
them locally at any time.

## How to run

**Easiest:** double-click `Run-Tests.bat` in this folder. It runs the whole suite and ends
with `RESULT: PASSED - no test failed ...`, or with `RESULT: FAILED` when a test failed or the
run did not start (for example because PowerShell could not be started). The exit code is 0
only when no test failed. Skipped and not-run tests are counted in Pester's summary, just
above the result line. The batch file resolves the path from its own location (`%~dp0`), so
it works from any clone.

**Manually** (from any terminal):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "Import-Module Pester; Invoke-Pester -Path '<path-to>\tests' -Output Detailed"
```

Expect no failed test. A few tests are skipped by design: the JSON-Schema test on Windows
PowerShell 5.1 (it needs `Test-Json -Schema`, which GitHub Actions has), the live skill-pin
check unless `FABRIC_AGENTIC_CATALOG_ROOT` is set, and the PowerShell 7 end-of-input case in
`Consent.Tests.ps1` when `pwsh` is not installed.

**PBIVIZ-focused runs.** `PBIVIZ.Alm.Tests.ps1` is the longest file (about an hour on
Windows PowerShell 5.1). While you work on the helper, run it alone, or one `Describe` block:

```powershell
$cfg = New-PesterConfiguration
$cfg.Run.Path = '.\tests\PBIVIZ.Alm.Tests.ps1'           # add PBIVIZ.Install.Tests.ps1 for the installer side
$cfg.Filter.FullName = 'Build isolation*'                # any Describe or It name, wildcards allowed
$cfg.Output.Verbosity = 'Detailed'
Invoke-Pester -Configuration $cfg
```

**Prerequisites and permissions.**

- Pester 5 or later (CI uses the current Pester), Git 2.28 or later, and Node.js on PATH for
  every PBIVIZ build test (the stand-in CLI is a Node script).
- No administrator rights, no network and no real remote. Repositories, bare remotes,
  junctions (`mklink /J`), deny-list ACLs and the stand-in toolchain are created under TEMP
  and removed afterwards.
- The developer's global and system Git configuration is hidden, and the build tests restore
  every environment variable they touch.
- No test reads or writes a real certificate store entry or the real
  `%USERPROFILE%\pbiviz-certs` folder. The certificate-store check is simulated by replacing
  the helper's read-only store probe.

**Windows PowerShell 5.1 and PowerShell 7.** The tests run on both: the maintainer runs
Windows PowerShell 5.1 locally (the installer's runtime), CI runs PowerShell 7. Behaviour that
exists only in 5.1 (for example `@($list)` on a `List[object]`) is pinned by an explicit test.

**Tests that start the installer.** Two kinds of test start the real installer script as a
child process. Neither can install anything.

- *Dry-run tests* (`Generated`, `SessionStatus`, `SkillMap`, `SkillCompat` and the installer
  side of `Housekeeping`) pass `-EmitAgentsTo`. The installer generates files and returns
  before any prerequisite, clone, install or launch code. `SkillMap` and `SkillCompat` then
  run `-VerifyRoot` on that output, which only re-hashes the generated files and exits.
- *Prompt tests* (`Step1Prompts` and the Step 1 part of `PBIVIZ.Install`) pass
  `-StopAfterStep1` through `Invoke-InstallerPromptCheck` in `Manifest.Helpers.ps1`. Three
  independent safeguards apply:
  1. The installer exits **by itself** at the end of Step 1, and again at script level before
     the prerequisite step.
  2. Before every launch the helper parses the script and **refuses to start it** unless
     everything reachable before that exit is on a short allow-list: no process start,
     download, package manager, registry or environment write, `Invoke-Expression` or
     installer function. `Step1Prompts.Tests.ps1` proves the refusal with unsafe variants of
     the script.
  3. Every optional install is behind a question that only a typed Yes passes, and the
     child's input is closed.

  The child also gets a throwaway `USERPROFILE` and a PATH holding only Windows folders plus
  tripwire stand-ins for `winget`, `pip`, `python`, `code`, `git`, `npm` and other commands.
  A stand-in records the call and fails; the tests assert that none was called. A timeout
  stops a hanging child as an emergency only; it is not what prevents installs.

Never add a test that runs the installer without one of these switches. `Consent` starts
a child PowerShell too, but it holds the consent functions only, not the installer.

**What the suite needs from the machine.** PowerShell must be able to start `powershell.exe`
(and `cmd.exe` to start PowerShell, for the dry-run tests), and Git must accept repositories it
creates under TEMP. Where endpoint policy blocks either for the calling process, the tests that
need it fail for that reason. The files that work in-process still run, apart from their few
cases that start a process or real Git: `Manifest`, `Hierarchy`, `Tools*`, `Version`,
`Neutrality`, `UpdateSafety`, `Pipeline`, `AiReadiness`, `Tooling`, `Consent`,
`PythonDetection`, `SetupHonesty`. Run the whole suite from an ordinary terminal with
`Run-Tests.bat`.

**Stand-in versus real SDK.** Every build in these tests uses a stand-in for the visual's
project-local `powerbi-visuals-tools`. Its modes reproduce the behaviours that matter: the
SDK's certificate check and `pwsh` call, a shell-less spawn, an API install attempt, hangs
and detached children. The real SDK, a real Azure DevOps remote, Power BI Desktop and the
multi-agent flow are covered by acceptance testing, not here (README
[3.11](../README.md#311-validation-compatibility-and-known-limitations)).

**Adding a regression test.** Reproduce the failure first, in the file that owns the code:

- PBIVIZ helper behaviour: `PBIVIZ.Alm.Tests.ps1`. Build fixtures with `New-TRepo`,
  `New-TVisual`, `Save-TAll` and `Install-TFakeTools -Mode <mode>`; for Level 3 use `New-TL3`
  and `Invoke-TPromotion`. The helper's single source is the `$pbivizAlmScript` heredoc in the
  installer; the tests load it from there.
- Installer functions: load them from the parsed installer (see `PythonDetection.Tests.ps1`).
- Generated content: `Generated.Tests.ps1`.

Keep the test offline and under TEMP, restore what you change, and quote Git flags that look
like `TGit` parameters (`'-r'`, `'-D'`). Never weaken an existing assertion to make a run
green.

**Refreshing the skill-map fixtures.** `skill-catalog.snapshot.json` and `agent-baseline.json`
under `tests/fixtures/` are committed evidence. Refresh them on purpose and review the diff;
never refresh them to make a run green.

- `skill-catalog.snapshot.json` is recorded from an installed workspace whose two clones are
  at the upstream commits you intend to support. It holds the relative path of every folder
  with a `SKILL.md` that sits directly in a skill container, any pinned reference that is not
  such a folder (for example a `references/*.md` file) with its type, and the two clone
  commits: identifiers only, no upstream text. Refresh it when a pin or alias changes, and
  only when every pin exists in that catalogue. To check that, first run `SkillMap.Tests.ps1`
  with `FABRIC_AGENTIC_CATALOG_ROOT` set to that workspace.
- `agent-baseline.json` is the identity baseline. For each of the 54 agents it records the
  name, description, invocability, tools, delegation targets and write permission. For 080-086
  it also records the pinned and suggested skills and a SHA-256 of the text from `## Playbook`
  to the end (LF-normalised). `Get-GeneratedAgentRecord` in `Manifest.Helpers.ps1` computes
  the same fields. Change the file only together with an intended change to an agent's
  identity, tools, hierarchy or the PBIVIZ team, and say so in the change description.

## What each file checks

| File | What it guards | Why it matters |
|------|----------------|----------------|
| `Manifest.Helpers.ps1` | *(not a test)* Shared helpers. They locate the installer, read the embedded manifest and the schema, hold the allowed tool set, load installer functions from the parsed script (`Get-InstallerFunctionLoader`) and build the skill-catalogue fixture and the agent record that `SkillMap` compares. They are also the only way tests start the installer for prompt checks: `Invoke-BoundedChild` (closed input, bounded wait), `Get-PromptCheckAnalysis` / `Assert-PromptCheckSafe` (static allow-list check) and `Invoke-InstallerPromptCheck` (`-StopAfterStep1`, replaced profile and PATH, tripwires). | Most test files load it; you never run it directly. |
| `Manifest.Tests.ps1` | In-process, on the embedded manifest. It parses as JSON, declares a `schemaVersion` and a semantic `productVersion`, and defines exactly **54 agents**: 3 executive, 8 team-lead, 43 worker. Ids, display names, file names and numeric file-name prefixes are unique, and ids are lowercase kebab-case. The manifest also validates against `schema/agent-manifest.schema.json`; that check needs `Test-Json -Schema` and is skipped on Windows PowerShell 5.1. | A duplicated, miscounted or malformed manifest cannot ship. |
| `Hierarchy.Tests.ps1` | In-process, on the delegation tree of the manifest. Parents: exactly one root (the Master), every `parent` resolves, and every parent chain reaches the Master without a cycle. Delegation: every `allowedChildren` entry resolves, only agents holding the `agent` tool delegate, workers never do, and the Master reaches every team lead and executive reviewer. Visibility: executives and team leads are visible and user-invocable; workers are hidden and not user-invocable. | The delegation tree cannot contain a loop, a dangling reference or an unreachable lead. |
| `Tools.Tests.ps1` | In-process. The `tools` entries of every agent and of the manifest default use only known capability tokens, without duplicates. The delegation tool (`agent`) is never granted to a worker or by the default set. | Keeps the capability model well-formed. |
| `Tools.LeastPrivilege.Tests.ps1` | In-process. Every agent declares an **explicit** `tools` array, so nothing relies on the default; the manifest default is **read-only** (`read`, `search`); only executives and team leads hold the `agent` tool; read-only diagnostic roles are never granted `edit`; no agent holds a token outside the approved set. | Least privilege: a broad capability is granted per role, never inherited. |
| `Version.Tests.ps1` | Four groups. **Version:** the installer's `$productVersion`, the manifest `productVersion`, the README `**Version:**` line, the `.bat` banner and window title, and the newest CHANGELOG entry (`## [vX.Y.Z]`, neutral or with its real release date) agree. | `Generated.Tests.ps1` | Runs the installer as a dry run (`-EmitAgentsTo`) into a temp folder and checks the **files it really generates**. A static guard keeps agent files free of constructs specific to one chat harness (not a runtime proof). Configuration: `starting-flow.md`, `working-flow-reference.md`, `Get-SessionStatus.ps1` and `.vscode/settings.json` are emitted as designed. PBIVIZ: the emitted `Pbiviz-Alm.ps1` is byte-identical to its source and holds no destructive Git command, all six `pbiviz-*` skills are emitted, `.vscode/mcp.json` carries `microsoftDocs`, and emit mode creates no PBIVIZ folder or mapping. Documents, skills and agents name a download-capable npm command only as a prohibition or behind `APPROVED:INSTALL`, and the release-correctness rules reach the release skills, 080, 086 and the CLI guide. | Checks the product the generator really emits, structure and specialist content, not only the manifest contract. |
| `VendorClone.Tests.ps1` | Loads `Update-VendorClone` from the installer and runs it against throwaway local bare repositories; no network. Refresh: a stale clone reaches `origin/HEAD` under `$ErrorActionPreference = 'Stop'`, local edits are stashed and not lost, a second call changes nothing, the caller's error preference is kept, and a missing path is skipped. Failure paths: a failed stash leaves the clone untouched (no reset), an unresolvable upstream is reported as *could not reset* and never as *already at upstream*, and a clone that lacks only `origin/HEAD` still refreshes through the `@{upstream}` fallback. | `Step1Prompts.Tests.ps1` | Runs the real installer through Step 1 only (`-StopAfterStep1`) as a child process with scripted answers. Prompts: `y` at *Enter 1 or 2* behaves as option 1; a full path typed at the *name* prompt (either option) is used as it is and never crashes `Join-Path`; an invalid folder name is sanitised; an unrecognised choice and a relative path for option 1 are asked again; a missing folder is created only on an explicit Yes (Enter, `n`, other text and end of input do not create it). Negative controls: unsafe variants of the script (the stop removed or made conditional; an install, a download, a process start, an environment write and others placed before it) are each refused before launch. ## What these tests do **not** cover

- **A real installation.** No test runs the installer end to end against a real Fabric or
  VS Code environment: no network, no tool installs.
- **How well an agent behaves.** The tests check the structure, required sections and safety
  rules of an agent file, not the quality of its prompt. That is judged in real use and by the
  installer's post-generation self-test (`guardrail-status.json`).
- **Remote services.** No test starts, signs in to or calls a remote MCP server, applies
  *Prep data for AI* content in Power BI or asks Copilot a question. `AiReadiness` and
  `Tooling` check the shipped text, the grants and the detection logic.
- **The real PBIVIZ toolchain.** See "Stand-in versus real SDK" above.
