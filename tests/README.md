# Test suite — what it guarantees

These [Pester](https://pester.dev) tests are the automated safety net for the
installer. They validate the **embedded agent manifest** (the `$agentManifestJson`
block inside `Setup-FabricAgenticWorkspace.ps1`) and its governance invariants, so
a change that would corrupt the agent organisation is caught before release.

They run automatically in GitHub Actions on every push/PR that touches the
installer, schema, or tests (see `.github/workflows/validate.yml`), and you can run
them locally at any time.

## How to run

**Easiest:** double-click `Run-Tests.bat` in this folder. It runs the whole suite
and shows a green/red summary. The path is resolved from the batch file's own
location (`%~dp0`), so it works for any user on any machine — no hard-coded paths.

**Manually** (from any terminal):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "Import-Module Pester; Invoke-Pester -Path '<path-to>\tests' -Output Detailed"
```

Expect **all tests passed / 1 skipped** on Windows PowerShell 5.1. The one skip is the
JSON-Schema test, which needs PowerShell 7 (`Test-Json -Schema`); GitHub Actions
runs on PowerShell 7, so it runs there and the full suite is exercised in CI.

**PBIVIZ-focused runs.** The PBIVIZ helper suite is the longest (about an hour on
Windows PowerShell 5.1); run it alone, or one `Describe` block, while you work:

```powershell
$cfg = New-PesterConfiguration
$cfg.Run.Path = '.\tests\PBIVIZ.Alm.Tests.ps1'           # add PBIVIZ.Install.Tests.ps1 for the installer side
$cfg.Filter.FullName = 'Build isolation*'                # any Describe or It name, wildcards allowed
$cfg.Output.Verbosity = 'Detailed'
Invoke-Pester -Configuration $cfg
```

**Prerequisites and permissions.** Pester 5+ (CI uses the current Pester), Git 2.28+, and
Node.js on PATH for every PBIVIZ build test (the stand-in CLI is a Node script). No
administrator rights, no network and no real remote are needed: repositories, bare remotes,
junctions (`mklink /J`), deny-list ACLs and the stand-in toolchain are created under TEMP
and removed afterwards, the developer's global and system Git configuration is hidden, and
the build tests restore every environment variable they touch. No test reads or writes a
real certificate store entry or the real `%USERPROFILE%\pbiviz-certs` folder: the
certificate-store check is simulated by replacing the helper's read-only store probe.

**Windows PowerShell 5.1 and PowerShell 7.** The suites are written for both. Locally the
maintainer runs Windows PowerShell 5.1 (the installer's runtime); CI runs PowerShell 7. A
PowerShell 5.1-only behaviour (for example `@($list)` on a `List[object]`, Canary D11) is
pinned by an explicit test.

**Stand-in versus real SDK.** Every build in these suites uses a stand-in for the visual's
project-local `powerbi-visuals-tools`; its modes reproduce the behaviours that matter (the
SDK's certificate check and `pwsh` call, a shell-less spawn, an API install attempt, hangs,
detached children). The real SDK, a real Azure DevOps remote, Power BI Desktop and the
multi-agent flow were exercised in the v0.8.0 Canary acceptance, not here (README
[3.11](../README.md#311-current-status-v080)).

**Adding a regression test.** Reproduce the failure first, in the file that owns the code:
PBIVIZ helper behaviour in `PBIVIZ.Alm.Tests.ps1` (build fixtures with `New-TRepo`,
`New-TVisual`, `Save-TAll`, `Install-TFakeTools -Mode <mode>`; Level 3 with `New-TL3` and
`Invoke-TPromotion`), installer functions by loading them from the parsed installer (see
`PythonDetection.Tests.ps1`), generated content in `Generated.Tests.ps1`. Keep it offline and
under TEMP, restore what you change, quote Git flags that look like `TGit` parameters
(`'-r'`, `'-D'`), and never weaken an existing assertion to make a run green. The helper's
single source is the `$pbivizAlmScript` heredoc in the installer; the tests load it from
there.

## What these tests do **not** cover

They validate the manifest **contract**, the generated files (structure and content
sections), the emitted settings and the vendor-refresh function. They do not run the
installer end-to-end against a real Fabric / VS Code
environment (no network, no tool installs), and they do not judge the
*behavioural* quality of an agent's prompt — only its structure, required sections and safety rules.
Behavioural quality is validated by real-world use and the installer's
post-generation self-test (`guardrail-status.json`).
